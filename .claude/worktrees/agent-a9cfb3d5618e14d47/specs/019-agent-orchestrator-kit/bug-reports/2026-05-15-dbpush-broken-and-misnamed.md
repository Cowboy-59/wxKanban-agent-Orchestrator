# Bug — `dbpush` is broken and contains a misplaced Drizzle migration side-effect

**Filed**: 2026-05-15
**Status**: open
**Severity**: P1 (CLI unusable; blocks spec-metadata sync workflow)
**Source files**:
- [wxkanban-agent/dbpush.ts](../../../wxkanban-agent/dbpush.ts)
- [wxkanban-agent/core/orchestrator/command-handlers/dbpush.ts](../../../wxkanban-agent/core/orchestrator/command-handlers/dbpush.ts)
- [wxkanban-agent/core/orchestrator/workflow-engine.ts](../../../wxkanban-agent/core/orchestrator/workflow-engine.ts) (already wired into dispatch; CLI is reachable)

---

## TL;DR

`dbpush` is intended to be a **spec-metadata sync** command — it reads local
`specs/NNN-*/{spec,plan,tasks,tests,quickstart}.md` + `lifecycle.json` and pushes
the validated metadata to the MCP Project Hub database. It is **not** a Drizzle
migration tool. Real schema migrations belong to the pattern documented in the
`reference_drizzle_migration_apply` memory (raw `pg.Client` + transaction).

Today, every CLI invocation fails with:

```
Validation errors:
Invalid JSON in specs/001-multi-platform-task/spec.md
Invalid JSON in specs/002-Scope/spec.md
... (one per spec folder)
```

There are four root causes stacked on top of each other. Fixing the surface bug
exposes the next one. This bug report captures all four plus the misplaced
migration side-effect that an earlier author welded onto the entry point.

---

## Bug 1 — Validator calls `JSON.parse` on Markdown files

[wxkanban-agent/dbpush.ts:32-46](../../../wxkanban-agent/dbpush.ts#L32-L46):

```ts
async function readAndValidate(filePath: string, schema: z.ZodSchema<any>) {
  const content = await fs.readFile(filePath, 'utf-8');
  let data;
  try {
    data = JSON.parse(content);                            // ← parses MD as JSON
  } catch {
    throw new Error(`Invalid JSON in ${filePath}`);        // ← user-visible error
  }
  const result = schema.safeParse(data);
  if (!result.success) {
    throw new Error(`Validation failed for ${filePath}: ${result.error}`);
  }
  return result.data;
}
```

[wxkanban-agent/dbpush.ts:122-138](../../../wxkanban-agent/dbpush.ts#L122-L138) then calls
this on every `spec.md` and `tasks.md` under `specs/`. `spec.md` is Markdown; the
first character is `#`, which `JSON.parse` rejects immediately. Every spec folder
produces an error. The errors array fills, and:

```ts
// dbpush.ts:140-142
if (validationReport.errors.length && !options.force) {
  throw new Error('Validation errors:\n' + validationReport.errors.join('\n'));
}
```

→ exit 1 with the wall of `Invalid JSON in ...` errors.

**Fix**: replace `JSON.parse` with a real `spec.md` parser that handles
Markdown frontmatter (e.g., gray-matter) plus structured section parsing.
Only `lifecycle.json` is legitimately JSON.

## Bug 2 — Zod schemas are unfinished placeholders

[wxkanban-agent/dbpush.ts:14-29](../../../wxkanban-agent/dbpush.ts#L14-L29):

```ts
const SpecSchema = z.object({
  id: z.string(),
  title: z.string(),
  // ...other fields
});
const TaskSchema = z.object({ id: z.string(), specId: z.string(), /* ... */ });
const LifecycleSchema = z.object({ /* ...fields */ });
```

Even if Bug 1 were fixed, the schemas have one or two fields and `// ...other
fields` comments. Real `spec.md` has dozens of structured sections, and
`lifecycle.json` (per `_wxAI/commands/push.md`) has nested objects for
progress/timeline/etc. The schemas would either:

- Pass everything (because they only check the trivial fields they declare), or
- Fail everything (if `z.strict()` were ever added)

**Fix**: define the real schemas matching the artifacts. Cross-reference
[`_wxAI/commands/push.md`](../../../_wxAI/commands/push.md) and the templates
generated by [`command-handlers/createspecs.ts`](../../../wxkanban-agent/core/orchestrator/command-handlers/createspecs.ts).

## Bug 4 — A Drizzle migration side-effect was welded onto the entry point and should be removed

[wxkanban-agent/dbpush.ts:48-101](../../../wxkanban-agent/dbpush.ts#L48-L101) defines
`maybeApplyKitMigrations()`, which:

1. Reads `DATABASE_URL` from env
2. Dynamically imports `pg`
3. Opens a transactional `pg.Client`
4. Calls `applyKitMigrations` from
   [`core/orchestrator/kit-migration-applier.ts`](../../../wxkanban-agent/core/orchestrator/kit-migration-applier.ts)

This is invoked unconditionally before validation at
[dbpush.ts:110](../../../wxkanban-agent/dbpush.ts#L110):

```ts
if (!options.dryRun) {
  await maybeApplyKitMigrations();
}
```

**Decision (2026-05-15)**: this side-effect is **out of scope** for `dbpush`. The
command name leads developers to expect "this is the migration tool" — but
`dbpush` is and should be spec-metadata sync only. Real Drizzle migrations are
applied via the pattern documented in the [[reference_drizzle_migration_apply]]
memory (raw `pg.Client` + transaction in a standalone script), not as a
side-effect of metadata sync.

**Fix**: remove `maybeApplyKitMigrations()` from `dbpush.ts` entirely. If a
kit-installed CLI command for migrations is needed, expose it under a separate
name (e.g., `kit:migrate`) so the operator's intent is unambiguous.

---

## Recommended fix order

1. **Remove** `maybeApplyKitMigrations()` from `dbpush.ts` and its call site
   (Bug 4). Smallest, safest, no downstream coupling. Confirms `dbpush` is
   purely spec-metadata sync.
2. **Define** the real Zod schemas for spec / plan / tasks / tests / lifecycle
   (Bug 2). Reference `_wxAI/commands/push.md` for the contract.
3. **Replace** `JSON.parse` with a Markdown frontmatter + section parser for
   `*.md` files; keep `JSON.parse` only for `lifecycle.json` (Bug 1).
4. **Implement** Phases 2–5 via the existing MCP tool surface (Bug 3). Use
   `BuildScopeWorker` as the reference HTTP client pattern.
5. **Tests** — vitest unit coverage for the parser + schema validation paths;
   integration test against a local MCP server (already exercised by
   `mcp-server/tests/`).

Total effort estimate: 2–3 dev days (Bug 4 = an hour; Bugs 1–3 = the bulk).

---

## Workarounds until fixed

- For actual Drizzle migrations: use [[reference_drizzle_migration_apply]] —
  generate via `drizzle-kit generate`, apply via a standalone `pg.Client`
  transaction. Do not invoke `dbpush` for this.
- For spec-metadata sync: call the MCP tools directly from the user's editor
  AI (`project.create_specs`, `project.upsert_document`, `project.create_task`)
  while reviewing each artifact. Tedious but it's the only path that works
  today.
