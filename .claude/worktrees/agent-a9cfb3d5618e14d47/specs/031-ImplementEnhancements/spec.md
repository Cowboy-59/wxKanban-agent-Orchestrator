# Spec 031: Implement Command Enhancements — Delete Action + Batch-by-Scope Mode

**Spec Number**: 031
**Status**: `proposed`
**Created**: 2026-05-16
**Depends On**: 019-agent-orchestrator-kit (the orchestrator being enhanced), 026-CodeFencing (the fence convention these enhancements operate within)
**Required By**: 030-StageGateConsolidation (cannot run its implementation phase until 031 ships), and every future ADR-0001 refactor scope (spec-parser consolidation, fence-writer consolidation, ...)
**Source**: in-conversation buildscope, 2026-05-16, promoted from `stub` after the spec 030 buildscope surfaced the prerequisite gap

---

## Overview

The wxkanban-agent kit's `implement` command, as it ships today, has two capability gaps that block refactor-shaped scopes from running through the orchestrator:

1. **No file deletion.** [`ProposedFile`](../../wxkanban-agent/core/orchestrator/implement-prompt.ts) accepts only `action: "create" | "modify"`. [`parseProposal()`](../../wxkanban-agent/core/orchestrator/implement-prompt.ts) explicitly rejects any other value. Refactors that consolidate code by removing old modules — Spec 030 deletes three files (`command-policy.ts`, `stage-enforcement.ts`, `command-policy.test.ts`); the queued spec-parser and fence-writer refactors will delete more — cannot perform those deletions through the orchestrator. The alternative is out-of-band `git rm`, which defeats the fence-history audit trail (deletions never appear in `taskfencehistory`) and breaks the orchestrator-first rule.
2. **No batch mode.** [`handleImplementCommand`](../../wxkanban-agent/core/orchestrator/command-handlers/implement.ts) takes `scope` and `task` as both required parameters. A multi-task scope requires N separate invocations. There is no `wxkanban-agent implement <scope>` form that walks `tasks.md` in dependency order and runs each `todo` task automatically. The 17-task Spec 030 plan would otherwise demand 17 separate CLI invocations.

This spec adds both capabilities. The existing `<scope>/<task>` invocation form is preserved as an **optional** surgical override — useful for re-running a single task in isolation.

The kit's existing principles are preserved by design:

- **Editor AI generates; kit applies.** Per Spec 019 R6a, the kit does not call AI. Both new capabilities operate on proposals generated by the user's editor AI, the same way the per-task flow does today.
- **Fences are orchestrator-written.** Delete actions emit fence-history rows; they never modify fence markers in surviving files.
- **Drift detection remains the safety net.** Deletion of a fenced unit consults the same content-hash drift check that modification uses; `--accept-drift` overrides apply identically.
- **Atomic transactions.** Multi-file proposals and batch-mode multi-task runs both respect the existing FS+DB transaction shape — partial success states should be rare and recoverable.

This spec ships:

- **`"delete"` value added to `ProposedFile.action`** in `implement-prompt.ts`; corresponding handler branch in `implement.ts` (drift check, atomic file removal, `taskfences` / `taskfencemodifications` / `taskfencehistory` cleanup inside the existing transaction).
- **`implement <scope>` invocation form** in the CLI gateway and the `handleImplementCommand` handler — loads the spec bundle, walks `tasks.md` in dependency order, invokes the existing per-task flow for each `todo` task. Honors `--dry-run` across the batch.
- **`<scope>/<task>` form preserved** as the optional surgical mode for re-running individual tasks.
- **Updated [`docs/implement.md`](../../wxkanban-agent/docs/implement.md)** — the current docs claim step 3 of `implement` "Builds an AI prompt and calls Gemini," which directly contradicts Spec 019 R6a and the actual code. This spec rewrites the docs to reflect what `implement` actually does.

The "Claude coworker" enhancement that lets the editor AI participate in the orchestration loop more deeply is **explicitly deferred** to a future scope after 031 ships.

## Functional Requirements

### FR-001 — `"delete"` action on ProposedFile
`wxkanban-agent/core/orchestrator/implement-prompt.ts` updates:

- The `ProposedFile` interface's `action` field accepts `"create" | "modify" | "delete"` (was `"create" | "modify"`).
- `parseProposal()` accepts `"delete"` as a valid action value and rejects anything outside the three. The existing rejection message for invalid actions remains byte-identical except for the now-three-value list.
- The system prompt (`SYSTEM_PROMPT` constant in `implement-prompt.ts`) is updated to instruct the AI: use `"delete"` when removing a file; `body` may be the empty string in this case (it is ignored by the handler).
- `--print-prompt` output reflects the updated instruction so editor-AI consumers see the delete action available.

### FR-002 — Delete branch in handleImplementCommand
`wxkanban-agent/core/orchestrator/command-handlers/implement.ts` is extended so that for each `ProposedFile` with `action === "delete"`:

1. The file's current content is loaded (`existsSync` + `readFileSync`). If the file does not exist at `absPath`, the handler throws `ImplementError(2, "cannot delete <path>: file does not exist")`. No "already absent → warning" softening. Idempotency comes from tasks.md status — once the task is marked `done`, batch mode skips it on re-run. A surgical re-run (`implement 030/T013`) that fails with missing-file is correct behavior: it signals an unexpected state (the file vanished out-of-band between runs) worth investigating, not silent recovery.
2. Existing fences for the file are loaded from `taskfences` via `loadExistingFencesForFile`.
3. The drift check (FR-003) runs against each loaded fence.
4. If `options.dryRun` is true, the file is added to a new `filesWouldDelete` list (mirrors `filesWouldWrite`) and the entry is added to `filesSkipped` for accounting.
5. Otherwise, the file is removed (`fs.unlinkSync` — the FS-level operation is itself atomic at the inode level on POSIX and on Windows for non-open files; no tmp-rename dance is needed for deletion).
6. The DB transaction (already open per the existing per-task transaction shape) writes the `taskfencehistory` rows per FR-004 and deletes the corresponding `taskfences` rows. `taskfencemodifications` rows tied to those fences are also removed (cascade-by-foreign-key if the schema enforces it, explicit delete otherwise).
7. The file's path is added to a new `filesDeleted: string[]` field on `ImplementResult` (FR-010).

Deletion errors (filesystem refusal, missing permissions) throw `ImplementError(3, ...)` and trigger the existing transaction rollback. The result is identical to today's behavior for write errors — the partial transaction does not commit, and no `taskfences` rows are removed.

### FR-003 — Drift check for delete
Before deleting a file, the existing drift check ([implement.ts:216-233](../../wxkanban-agent/core/orchestrator/command-handlers/implement.ts#L216-L233)) is applied to every fence in the file. The check semantics are unchanged:

- For each existing fence row, the body is extracted from current file content using `linestart`/`lineend`.
- `isDriftDetected(body, fence.contenthash)` is called.
- If any fence reports drift and `options.acceptDrift` is not set, the handler throws `ImplementError(1, "<path>: fence [SCOPE <ownerscope> / <ownertask>] modified out of band. Use --accept-drift to overwrite (logged), or revert manual changes and retry.")` — byte-identical to today's modify-path message, with no special "delete" wording added.
- If `options.acceptDrift` is set, the deletion proceeds; FR-004 records each affected fence's history row with `delete-with-drift` instead of `delete`.

Unfenced content in the file does not participate in the drift check (consistent with today's behavior for modify; deliberate per the buildscope decision — unfenced content is Spec 026's concern).

### FR-004 — `taskfencehistory` contract for delete
For each `taskfences` row associated with a deleted file's path, a corresponding `taskfencehistory` row is inserted **before** the `taskfences` row is removed (preserving referential integrity / preserving the audit detail for archaeology):

- `action`: `"delete"` (or `"delete-with-drift"` if `--accept-drift` was used to override a drift detection on the same fence in the same operation).
- `ownerscope` and `ownertask`: copied from the deleted `taskfences` row — preserving the original owner.
- `description`: copied from the deleted `taskfences` row.
- `contenthash`: copied from the deleted `taskfences` row (the last-known good state at deletion time).
- `linestart` / `lineend`: copied (the position at deletion time).
- `createdat`: now.
- `appliedby`: the current scope/task tuple performing the deletion (the deleting task — e.g., `030/T013` for the Spec 030 use case).

The `taskfences` row is removed after the `taskfencehistory` row is written, inside the same transaction. The `taskfencemodifications` rows tied to the deleted fence are removed in the same transaction (kept for archaeology if the schema relates them to history via FK; otherwise dropped, mirroring the kit's existing modify-path data lifecycle).

### FR-005 — `implement <scope>` invocation form
The CLI gateway (`wxkanban-agent/apps/command-gateway/src/cli.ts`) and `handleImplementCommand` accept an invocation with `<scope>` only (no task argument):

- `wxkanban-agent implement 030` — batch mode; walks `tasks.md` for scope 030 in dependency order.
- `wxkanban-agent implement 030/T013` — surgical mode (today's behavior, preserved); operates on T013 only.
- Both forms accept the existing flag set (`--dry-run`, `--accept-drift`, `--file`, `--specs-root`, `--project-id`, `--input`, `--print-prompt`).
- A new flag, `--continue-on-error`, is added for batch mode (FR-007). It has no effect on surgical mode.

Argument shape disambiguation: a positional matching `^[0-9]{3}$` is treated as scope-only (batch); a positional matching `^[0-9]{3}/T[0-9]+$` is surgical. Other shapes throw `ImplementError(2, "invalid <scope> or <scope>/<task> argument: <given>")`.

### FR-006 — Dependency-ordered task walk
In batch mode, the orchestrator computes the execution order from `tasks.md`:

- Loads the spec bundle and parses tasks with their dependencies (the existing `findTask` + `verifyTaskUnblocked` paths in `spec-loader.ts` already understand dependencies).
- Filters to tasks with `status: todo` (skipping `done` and any other status).
- Topologically sorts the remaining `todo` tasks by their declared dependencies (a task whose dependencies all resolve to non-existent or `done` tasks is ready immediately; tasks awaiting `todo` dependencies wait for those to complete).
- Executes ready tasks sequentially in order; after each task completes successfully and is marked `done`, recomputes the ready set.
- If the dependency graph contains a cycle (defect in tasks.md), throws `ImplementError(2, "tasks.md dependency cycle detected: <task ids in cycle>")` before any task runs.

Parallel execution is explicitly out of scope; tasks run one at a time.

### FR-007 — Stop-on-failure default + `--continue-on-error`
By default, a failure in any task halts the batch immediately:

- The failing task's transaction is rolled back (existing per-task transactional behavior — unchanged).
- Tasks already completed in this batch remain `done` in tasks.md (their commits stand; no batch-wide rollback).
- Tasks not yet attempted remain `todo` and are not run.
- The CLI exits with the failing task's exit code (1, 2, or 3 per the existing `ImplementError` semantics).
- The summary (FR-009) reports the partial outcome: tasks completed, the failing task and its error, tasks not attempted.

With `--continue-on-error`, the batch continues past failures:

- Each failed task's transaction is still rolled back individually; the next task runs anyway.
- Tasks whose dependencies are unsatisfied (because a dependency task failed) are **skipped**, not attempted; their tasks.md status remains `todo`.
- The CLI exits with the highest exit code seen across all failures (1, 2, or 3); exits 0 only if every task succeeded.
- The summary reports a row per task: succeeded / failed / skipped (with reason — failed task ID for skipped-by-dependency).

### FR-008 — Apply-then-prompt-next state visibility
In batch mode, each task is fully applied (file writes + DB commits + tasks.md status update) before the next task's prompt is emitted:

- The orchestrator emits task N+1's prompt only after task N has committed.
- The proposal source for task N+1 (stdin per the existing `--input -` mechanism, with batch mode reading from stdin between tasks) generates its content with full visibility of task N's on-disk and DB changes.
- This naturally satisfies cross-task dependencies (e.g., T006's adapter can import the `Capability` enum from T001's `capabilities.ts` because the file is on disk when T006's proposal is generated).
- **Consequence**: batch mode without a driver actively responding to prompts will block on stdin read. This is correct behavior — `implement <scope>` is interactive in the kit's "no internal AI" model (Spec 019 R6a). The current user-facing pattern is "the editor AI drives the loop"; future iterations (Claude coworker scope, deferred) will make this more ergonomic without changing the contract.

No new transport, no proposal-pre-staging, no manifest-passing mechanism. The existing per-task stdin flow extended to a loop is the entire mechanism.

### FR-009 — Dry-run aggregation
With `--dry-run` in batch mode (`implement <scope> --dry-run`), the orchestrator emits a summary table to stdout after all tasks are processed (no files written, no DB commits):

```text
Task | Title                                    | Files                         | Warnings
T001 | Create capabilities.ts                   | +1 create                     | 0
T002 | Create policy.ts                         | +1 create                     | 0
...
T013 | Delete old surfaces                      | -2 delete                     | 0
T017 | Cleanup pass                             | ~3 modify                     | 0
                                                                       Total: 17 tasks
                                                                              15 creates, 3 modifies, 2 deletes
                                                                              0 warnings
```

- `+N create`, `~N modify`, `-N delete` syntax for visual distinction.
- Per-task warnings counted but not detailed in the summary.
- Total row aggregates across all tasks.
- `--verbose` flag opts into per-task detail — equivalent to running each task with the existing per-task dry-run, concatenated with task-id headers between them.
- `--dry-run` in surgical mode (`implement <scope>/<task> --dry-run`) behaves exactly as today (per-task detail). Summary mode is batch-only.
- A future `--json` flag (deferred — not part of this scope) would emit the same data in machine-readable form. The summary-row data structure is internally separable to make that addition non-breaking later.

### FR-010 — ImplementResult shape extended
`wxkanban-agent/core/orchestrator/command-handlers/implement.ts` extends `ImplementResult`:

```ts
export interface ImplementResult {
  exitCode: 0 | 1 | 2 | 3;
  message: string;
  filesWritten: string[];
  filesSkipped: string[];
  filesDeleted: string[];   // NEW
  warnings: string[];
  prompt?: { systemPrompt: string; userPrompt: string };
}
```

The human-readable `message` field is updated to include deletions when present:

- Today: `implement 030/T013 — wrote 0 file(s), skipped 0, 0 warning(s)`
- After: `implement 030/T013 — wrote 0 file(s), deleted 2, skipped 0, 0 warning(s)`

The "deleted N" component is **omitted** when `filesDeleted.length === 0`, preserving today's message for create/modify-only tasks (no spurious "deleted 0" noise). This preserves backwards-compatibility for any consumer that parses today's message format.

In batch mode, the orchestrator returns an aggregate `BatchImplementResult` (new type) wrapping the per-task results:

```ts
export interface BatchImplementResult {
  exitCode: 0 | 1 | 2 | 3;   // highest exit code across tasks; 0 only if all succeeded
  tasks: Array<{
    taskId: string;
    result: ImplementResult | { status: 'skipped'; reason: string };
  }>;
  summary: {
    succeeded: number;
    failed: number;
    skipped: number;
    totalFilesWritten: number;
    totalFilesDeleted: number;
    totalFilesModified: number;
    totalWarnings: number;
  };
}
```

The CLI gateway formats this into the summary table from FR-009 for human consumption.

### FR-011 — Surgical mode preservation
The `wxkanban-agent implement <scope>/<task>` form behaves exactly as today, with the only changes being:

- The `delete` action is now valid in proposals (per FR-001/002), regardless of mode.
- The `ImplementResult.message` includes the "deleted N" component when `filesDeleted` is non-empty (per FR-010).

No other behavior changes. Every flag works as today. Every existing call site (scripts, integration tests, the kit's own self-implementation tooling) continues to function with no modification beyond updating to consume the new `filesDeleted` field if it cares about deletions (callers that ignore the new field are unaffected).

### FR-014 — Acceptance criteria
This spec is complete when all the following hold:

1. `ProposedFile.action` accepts `"create" | "modify" | "delete"`; `parseProposal` validates all three and rejects others (FR-001).
2. The delete branch in `handleImplementCommand` applies the existing drift check, writes `taskfencehistory` rows per FR-004, removes the `taskfences` rows in the same transaction, and atomically removes the file from disk (FR-002, FR-003).
3. Missing-file deletion fails hard with `ImplementError(2, ...)` (FR-002 #1).

5. Batch mode walks tasks in dependency order, detects cycles, runs sequentially (FR-006).
6. Default failure semantics halt the batch; `--continue-on-error` opts into continue-and-skip behavior (FR-007).
7. Apply-then-prompt-next state visibility is implemented; each task's proposal is sourced after the prior task has committed (FR-008).
8. Batch `--dry-run` emits the summary table; `--verbose` expands to per-task detail (FR-009).
9. `ImplementResult.filesDeleted` exists; per-task message includes "deleted N" when non-empty; `BatchImplementResult` aggregate type is implemented (FR-010).
10. Surgical-mode behavior is unchanged except for the additive concerns above (FR-011).
11. `wxkanban-agent/docs/implement.md` no longer states "calls Gemini"; documents batch mode, delete action, `--continue-on-error`, and `--dry-run --verbose` (FR-012).
12. All test files in FR-013 exist and pass.
13. The kit's package version is bumped one minor revision (matching the spec 030 versioning pattern); `wxkanban-agent/CHANGELOG.md` documents both the delete-action and batch-mode additions plus the docs correction.
14. All new top-level code units carry the `// [SCOPE 031 / T0NN] BEGIN/END` fence written by the orchestrator (per Spec 026). Since this spec modifies `implement.ts` itself, the first implementation tasks use the direct-import wrapper per project memory; later tasks (after the enhanced `implement` is functional) can use it on itself.
15. A `wxkanban-agent auditfences --strict` run returns exit 0.

## User Scenarios & Testing

This section enumerates **concrete behavioral scenarios** for the new capabilities — pre-merge manual smoke gate (FR-014 #12). Unit-level coverage is FR-013.

### Delete action

| Scenario | Setup | Expected outcome |
|---|---|---|
| Clean delete (no drift) | Proposal with `action: "delete"` for a file whose fenced units match their last orchestrator-written content | File removed atomically; `taskfences` rows removed; `taskfencehistory` rows written with `action: "delete"`; tasks.md status `done`; result message includes "deleted N". |
| Delete with drift, no override | Same setup; a fenced block in the target file has been hand-edited since the orchestrator last wrote it | `ImplementError(1, "<path>: fence [SCOPE <s> / <t>] modified out of band. Use --accept-drift to overwrite (logged), or revert manual changes and retry.")` — byte-identical to today's modify-path drift message. No file change, no DB change. |
| Delete with drift, `--accept-drift` | Same setup with `--accept-drift` flag | File removed; `taskfencehistory` rows written with `action: "delete-with-drift"` instead of `"delete"`; override logged. |
| Delete missing file | Proposal with `action: "delete"` for a path that doesn't exist on disk | `ImplementError(2, "cannot delete <path>: file does not exist")` — hard fail per FR-002 #1. No silent recovery. |
| Delete file with no fences | Proposal with `action: "delete"` for a path that exists but has no rows in `taskfences` | File removed; no `taskfencehistory` rows written (nothing to log); tasks.md status `done`. |
| Delete in `--dry-run` | Same as clean delete but with `--dry-run` | No file change, no DB change; result message reports "deleted N file(s)" but `filesDeleted` is empty (mirroring today's dry-run accounting). |

### Batch mode

| Scenario | Setup | Expected outcome |
|---|---|---|
| Happy path | `wxkanban-agent implement 030`; all 17 tasks have proposals available via stdin in order; no drift; no dependency cycles | All tasks run sequentially in dependency order; each commits before next prompt emitted; final exit code 0; summary table shows 17 succeeded. |
| Stop on failure (default) | Same setup; T005's proposal contains a parse error | T001–T004 commit; T005 fails with `ImplementError(3, ...)` from `parseProposal`; T005's transaction rolled back; T006–T017 not attempted; exit code 3; summary reports partial outcome. |
| `--continue-on-error` | Same setup with `--continue-on-error`; T005 fails; T010 also fails; T006–T009 and T011–T017 succeed | T001–T004 commit; T005 rolls back; T006–T009 commit (no dependency on T005); T010 rolls back; tasks depending on T005 or T010 are skipped (tasks.md stays `todo`); remaining tasks commit. Exit code is highest seen (3 in this case). Summary shows succeeded / failed / skipped with reason. |
| Batch `--dry-run` | `wxkanban-agent implement 030 --dry-run` | Summary table printed; no files written; no DB rows. |
| Batch `--dry-run --verbose` | Same with `--verbose` | Summary table plus per-task detail concatenated below, each headed with task ID. |
| Cycle detection | `tasks.md` declares T005 depends on T010 and T010 depends on T005 | `ImplementError(2, "tasks.md dependency cycle detected: T005, T010")` thrown before any task runs; no file change, no DB change; exit code 2. |
| Idempotent re-run after partial batch | Run `implement 030`; T005 fails; fix the issue (regenerate T005's proposal); re-run `implement 030` | T001–T004 already `done`, skipped; T005 onward runs fresh; T005 commits; T006–T017 follow. |
| Batch on empty scope | `implement 030` where all tasks are already `done` | Exit code 0; summary table reports "no tasks to run"; no error. |

### Surgical mode preservation

| Scenario | Setup | Expected outcome |
|---|---|---|
| Existing per-task flow | `wxkanban-agent implement 030/T001 --input proposal.json` | Behaves exactly as today; no shape changes to the success message except the additive "deleted N" component when relevant. Every existing flag works unchanged. |
| Surgical delete | `wxkanban-agent implement 030/T013 --input proposal.json` with a proposal containing `action: "delete"` | Same as the corresponding batch-mode delete scenarios but for a single task. |
| Surgical with `--continue-on-error` | Flag has no effect in surgical mode; flag is silently ignored | Single-task run completes or fails as today; no warning, no error about the irrelevant flag. |

## Risks & Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| `ProposedFile.action` union expansion breaks consumers | Low — TypeScript union additions are backwards-compatible at the type level; existing callers using `"create" \| "modify"` still satisfy the wider type | No mitigation needed at the type level. The only behavioral concern is `parseProposal`'s rejection message — its new three-value list could break code string-matching on the old two-value list. FR-001 keeps the message structure stable; verify with grep before merging. |
| `--continue-on-error` masks real failures | Medium — a user habituated to `--continue-on-error` may not notice that 5 of 17 tasks silently skipped | Exit code is the highest seen — non-zero exits propagate; summary table makes failures and skips visible; FR-009 summary format puts the failed/skipped row counts prominently. Documentation should warn against making `--continue-on-error` a default in scripts. |
| Batch mode blocks on stdin without driver | Medium — running `implement 030` interactively in a terminal without piping a proposal source will appear to hang | Documented as correct behavior in FR-008 and FR-012 (docs rewrite). A user-friendly improvement (timeout + helpful error after N seconds of stdin idle) is deferred to the "Claude coworker" scope where it has clearer requirements. Workaround today: emit prompt with `--print-prompt`, then re-invoke with `--input <file>` per task. |
| `docs/implement.md` drifts again after this rewrite | Medium — the previous drift went undetected for at least the duration between Spec 019 R6a landing and this scope | The chicken-and-egg note in FR-014 #14 documents the contract between docs and code. A future spec could add a doc-validation script that asserts key claims in `docs/implement.md` against actual code paths; out of scope here but tracked. |
| Chicken-and-egg: spec 031 enhances `implement`, but the spec must be implemented by `implement` | Medium — bootstrap problem; how do we run T001 of spec 031 when T001's job is to add the delete action that won't exist until T001 ships | Per project memory `feedback_orchestrator_cli_broken`, the direct-import wrapper is used for the first few tasks; once the enhanced `implement` works (likely after the batch-mode tasks land), the remaining tasks can be dogfooded through the enhanced surface. FR-014 #14 codifies this. |
| Test fixture maintenance burden | Low — a fixture scope in the repo is one more thing that can drift from the actual spec format | Keep fixture minimal (3 tasks, no exotic dependencies); fixture lives next to the integration test that uses it (`batch-against-fixture-scope.test.ts`); update via the same review path as any other code change. |
| Spec 030 unblocked-but-waiting | Low — spec 030 paper work is complete but its implementation phase blocks until 031 ships | Tracked explicitly in spec 030's plan.md Pre-Implementation Gates. No new risk introduced by 031; this is the state both specs have been planned around. |

## Out-of-Band Issues to Track Separately

1. **Other broken commands per Spec 019.** `buildscope --edit`, `createspecs`, `dbpush` are reportedly broken at the CLI layer per project memory. Spec 031 fixes `implement`; the others remain Spec 019's responsibility. The `implement` enhancements may indirectly improve confidence in routing the other broken commands' fixes through similar patterns, but they are not in scope here.
2. **"Claude coworker" enhancement.** The eventual ergonomic-improvement scope that lets the editor AI participate in the batch loop more deeply (without requiring stdin pipe choreography). Explicitly deferred from spec 031 per the original stub. Likely depends on spec 031 being complete.
3. **MCP-side batch mode question.** `project.implement` on the MCP surface today is per-task. Whether MCP should grow an equivalent batch capability is a separate decision — likely no, because MCP calls are inherently one-shot from the editor AI's perspective, and the AI is the natural driver of any cross-task loop. Track as a question for the "Claude coworker" scope; not in spec 031.
4. **Doc-validation tooling.** The fact that `docs/implement.md` drifted so badly suggests a structural problem — docs can claim things the code doesn't do, and nothing checks. A future small scope could add a doc-validation script (e.g., assert that the documented step 3 doesn't contain the word "Gemini" or "OpenAI"). Lightweight, useful, not in 031.
5. **Topological-sort helper extraction.** If FR-006's implementation requires a new helper in `spec-loader.ts` (the existing `verifyTaskUnblocked` may not expose ordering), the new helper is in scope here. If it cleanly reuses what exists, no change. Implementer note flagged in FR-006.
