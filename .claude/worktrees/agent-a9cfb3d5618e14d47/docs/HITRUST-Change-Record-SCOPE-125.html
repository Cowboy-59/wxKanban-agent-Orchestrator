Conversion Credential Redaction

Legacy-application conversion tooling copies source text verbatim into artifacts that are committed as project data and read into AI context on every subsequent session. Where the legacy source hardcodes database credentials, those values are reproduced and disclosed. This record documents the defect, its risk, the control being implemented, and what the control cannot remedy.

Framework applicability — read first

HITRUST is not currently an enabled framework for this project. The active compliance context returns SOC 2 only. This record is therefore prepared as advance documentation against the HITRUST SDLC rules held in the repository, not as evidence drawn from an active HITRUST assessment programme.

Control references below are taken from the repository's own HITRUST_SDLC_Compliance_Rules.md, which uses a local category taxonomy (01–17). An external assessor working from HITRUST CSF v9.x or v11 reference numbering will need a crosswalk; these references should not be presented to an assessor as CSF control identifiers without one.

01Change summary

A credential-redaction boundary is introduced into all three legacy-conversion families. Credential values are replaced with stable placeholder tokens at the point of extraction. The fact and location of each hardcoded credential is preserved and reported, because an inventory of which legacy procedures hardcode credentials is required output for both the migration and the rotation that must follow.

The change covers both producers of conversion artifacts — the Python extraction scripts and the AI session itself — introduces the shared write boundary the emitters never had, adds a read-only scan mode so already-converted projects can determine their existing exposure, and guards the deployed module copies against divergence.

02Trigger — reported security event

Finding f99e80aa was raised on an AI session performing a secrets-egress review of a consuming project. It reported that credential literals extracted from WEBDEV source were present as quoted string assignments in two git-tracked conversion artifacts, committed since 1ab3d5c, neither gitignored. The 2.4 MB source documentation PDF was also tracked at repository root.

The report disclosed paths and line numbers only. No credential value appears in the report, in the scope document, or in this record.

Root cause

No redaction stage exists at any point in any conversion family. Verified 2026-08-10 by search across all eighteen conversion scripts: the single match is an unrelated SQL-identifier sanitiser. In the reported family the path is direct and unbroken — page text is cleaned for character encoding only, becomes the page body, and every emitted file is assembled from those bodies.

The deeper cause is architectural rather than a missing pattern: credential handling has no owner. Eighteen scripts per tree each emit independently, several through unmediated file writes, and one artifact class has no producer script at all.

03Risk assessment

Why standard controls did not catch this

Conversion output is project data, not configuration. It is committed deliberately, because it is the rebuild source material. Every filename-based protection — environment-file deny rules, key-file patterns, gitignore convention — is keyed on files nobody intends to commit. This exposure arrives in files everybody intends to commit.

Exposure paths

Three compounding disclosures
PathRecipientReversible
Committed to version control Anyone with repository access, now and retrospectively No — history rewrite does not remove the credential from the legacy source
Read into AI context during implementation Model provider, on every session touching a conversion artifact No — already transmitted
Present in the tracked source documentation export Same as version control No

Assessment

Likelihood: high. Hardcoded connection credentials are idiomatic in all three legacy platforms. WinDev HFSQL blocks assign user and password literals directly; VB6 forms carry inline connection strings; the third platform's data dictionaries place the full connection string, credentials included, in the file owner attribute. A conversion of a credential-bearing application leaks by default, not by mistake.

Impact: high. Disclosure of live database authentication credentials, with no detection signal at any point and no record that disclosure occurred.

Detectability before this change: none. There is no warning, no summary, and no log. The reporting project discovered the exposure only through a dedicated review.

Design constraint of note

Only quoted literals are redacted. Parameter passing and variable references — a password assigned from an argument or a configuration variable — are deliberately left intact, so the analytical record of which procedures handle credentials survives the control. A redaction stage that removed credential-bearing code entirely would satisfy a naive reading of the requirement while destroying the evidence the migration and the rotation both depend on.

08Required actions outside this change

The following are necessary to close the finding and cannot be delivered by the change. Recording them here prevents the change from being read as full remediation.

  1. Rotate the affected legacy accounts. Owner: the reporting project's development team. This is the only remedy for credentials already disclosed, and it remains necessary whatever is shipped here. Governed by 02.d.1.
  2. Untrack the affected artifacts and the source export in the reporting repository, and decide whether the source documentation belongs in version control or in a controlled store the conversion reads from.
  3. Determine whether HITRUST should be enabled as an active framework for this project. It is not currently, and this record is advance documentation rather than assessment evidence until it is.
  4. Produce a CSF crosswalk if these references are to be presented to an external assessor, since the repository taxonomy is local.
