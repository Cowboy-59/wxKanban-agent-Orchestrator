1. KI-Engine und Abonnements
⚠️
Ein Wort zu den Nutzungsgrenzen. Eine umfangreiche technische Dokumentation zu konvertieren und anschließend implement über Dutzende Scopes laufen zu lassen, verbraucht viele Token. Mit einem Pro-Tarif können Sie mitten in einer Phase an eine Nutzungsgrenze stoßen. Das ist kein Fehlschlag — Ihre Arbeit liegt auf der Festplatte und in Git. Warten Sie, bis die Grenze zurückgesetzt wird, und setzen Sie mit demselben Befehl fort.
2. Arbeitsumgebung
💡
Installieren Sie diese Werkzeuge in dieser Reihenfolge. Jedes wird mit einem Befehl überprüft, damit Sie wissen, dass es funktioniert, bevor Sie weitergehen. Schließen Sie unter Windows nach jeder Installation VS Code und Ihr Terminal und öffnen Sie beide erneut, damit das neue Werkzeug erkannt wird.

git --version
irm https://claude.ai/install.ps1 | iex

Oben Windows (PowerShell). Verwenden Sie unter Mac / Linux curl -fsSL https://claude.ai/install.sh | bash. Schließen Sie danach das Terminal, öffnen Sie es erneut und prüfen Sie mit claude --version.

pip install pymupdf

3. Die MCP-Verbindung
💡
Die Spezifikations-Pipeline läuft über die MCP-Werkzeuge von wxKanban — den gehosteten Dienst unter mcp.wxperts.com, der den Lebenszyklus durchsetzt und Ihr Projekt speichert. Das Kit richtet das für Sie ein, sobald Sie den Projektordner in Phase 2 öffnen; es gibt keine Konfigurationsdatei zum Bearbeiten und keinen Schlüssel zum Einfügen. Sie müssen es nur bestätigen und wissen, wie Sie es reparieren.
node scripts/init.mjs

Ein fehlendes Werkzeug ist ein Einrichtungsproblem, kein Abrechnungsproblem. Nur ein ausdrücklicher 401-/Abonnement-Fehler ist ein Abrechnungsproblem.

2. Ihren Projektordner verbinden

Einmalig, nachdem Sie das Kit in Phase 2 heruntergeladen und entpackt haben.

3. Die Gewohnheit, die Sie rettet
git add . git commit -m "checkpoint before implement <scope number>"
💡
Den Checkpoint einlösen. Hat das implement etwas erzeugt, das Sie nicht wollen, listen Sie Ihre letzten Commits auf, suchen den angelegten Checkpoint und setzen den gesamten Ordner darauf zurück. git log --oneline -5 gibt je Commit eine Kurz-ID und eine Nachricht aus, neueste zuerst — zum Beispiel a3f9c21 checkpoint before implement 042. So versetzt git reset --hard a3f9c21 jede Datei exakt in den Zustand vor dem Lauf dieses implement. Ist Ihr Checkpoint schlicht der letzte Commit, leistet git reset --hard HEAD dasselbe, ohne dass Sie eine ID nachschlagen müssen.
git log --oneline -5 git reset --hard <commit-id>
⚠️
git reset --hard ist ein grobes Werkzeug. Es verwirft nicht committete Änderungen und löscht jeden Commit nach dem angegebenen. Bevor Sie es einsetzen, sollten Sie die zwei sanfteren Optionen kennen.

Die Dokumentation erzeugen
⚠️
Auf den Code kommt es an. Eine Dokumentation, die ohne den WLanguage-Code gedruckt wird, ergibt ein PDF, das vollständig aussieht und sich in leere Scopes verwandelt. Setzen Sie vor dem Drucken die Haken für den Code.
💡
Warum der Navigationspfad, und was tun, wenn er fehlt. Der Konverter ordnet jede Seite über ihr Type-Segment ein (Window, Query, Report, Procedure set, Analysis…), nicht über die Part-Nummer — die Teilnummerierung von PCSoft verschiebt sich zwischen Exporten, deshalb macht der Text des Navigationspfads die Aufteilung verlässlich. Fehlt er, scheitert die Konvertierung laut, niemals stillschweigend: Die Aufteilung lässt sämtliche Seiten unerfasst in pre-convert/_discarded.md und die Konsole meldet NOT CAPTURED. Die Korrektur ist klein — der Splitter stützt sich auf diese eine Zeile je Seite und lässt sich an das anpassen, was Ihr Export oben ausgibt. Schicken Sie uns den Rohtext der obersten Zeile einer Inhaltsseite.
Woher Ihr Datenmodell kommt
💡
Sie nutzen kein HFSQL / keine HF-Dateien? (Sie sind auf PostgreSQL, MSSQL, MySQL, SQL Server…) Dann können Sie beim Erzeugen der Dokumentation die Analyse weglassen. Sagen Sie der KI stattdessen, welche Datenbank Sie verwenden, und sie holt das Schema nach Abschluss der Konvertierung direkt aus dieser Datenbank — es muss nicht aus dem PDF rekonstruiert werden.

Sie nutzen HFSQL / HF-Dateien? Nehmen Sie die Analyse auf, damit das Schema erfasst wird, und migrieren Sie die eigentlichen Daten wie in Phase 5 beschrieben.

1. Das Ziel wählen
💡
Wie das mit der Stack-Auswahl zusammenhängt (Abbildung 3). Ihre Stack-Wahl liefert den hier angebotenen Vorgabewert — wählen Sie im Stack PostgreSQL, ist PostgreSQL vorausgewählt. Geschrieben wird tatsächlich die Antwort, die Sie an dieser Stelle geben; ändern Sie sie, ändern Sie auch den Stack, statt beide widersprüchlich stehen zu lassen.
💡
Warum „originalgetreu“. Behalten Sie Ihre HFSQL-Namen, entsprechen sich konvertierter und ursprünglicher Code eins zu eins, sodass Sie beide direkt vergleichen können, wenn etwas seltsam aussieht. Während einer Migration umzubenennen ändert zwei Variablen gleichzeitig und erschwert jede Fehlersuche. Das erzeugte DDL sagt das unmissverständlich — -- Names and types kept FAITHFUL (1:1) per the conversion choice. Benennen Sie später um, wenn die Anwendung läuft und Ihre Tests grün sind.

⚠️

Im Team arbeiten (Check-out / Check-in)
0 / 7
💡
Worum es geht: das Check-out aus dem SCM von WinDev, das Sie bereits kennen, angewendet auf Scopes. Git hat bewusst kein Signal dafür, „wer woran arbeitet“ — das ist Aufgabe eines Trackers, und wxKanban ist dieser Tracker. Einen Scope auszuchecken reserviert ihn für alle im Projekt auf Ihren Namen und legt in einem Zug den zugehörigen Git-Branch an.

So verteilen Sie in einem großen Projekt die Arbeit auf mehrere Entwickler und halten trotzdem alle zusammen — jede Person nimmt ihre eigenen Scopes, auf ihrem eigenen Branch, und alle sehen, wer was hat.
1. Einen Scope auschecken
git branch --show-current
💡
Die Spezifikationsdokumente eines Scopes öffnen sich in Ihrem Editor schreibgeschützt, wenn nicht Sie die Reservierung halten. Das ist ein weicher Schutz davor, versehentlich den Scope einer anderen Person zu bearbeiten, keine Sperre für Ihre eigene Arbeit.
2. Einen Scope wieder einchecken
👤
Arbeiten Sie allein? In einem Projekt mit nur einem Mitglied gibt es niemanden, mit dem Sie kollidieren könnten, daher sind die Reservierungen abgeschaltet und das Cockpit zeigt keine Sperrsymbole. Die Funktion erwacht in dem Moment, in dem ein zweiter Entwickler dem Projekt beitritt.
🔗
Wechseln oder mergen Sie Branches mit reinem Git statt über das Cockpit, hält ein vom Kit installierter Git-Hook die Reservierung im Gleichschritt, damit der Branch, auf dem Sie sind, und der Scope, den Sie halten, nicht auseinanderlaufen.
✅
Diese Phase ist abgeschlossen, wenn: jeder Entwickler im eigenen Cockpit sieht, wer welchen Scope hält, und git branch --show-current zu dem Scope passt, den die jeweilige Person ausgecheckt hat.

Ihr Code, Ihre Daten
⚠️
Ihr PDF der technischen WinDev-Dokumentation enthält Ihren Quellcode und Ihre Geschäftslogik. Es zu konvertieren bedeutet, diesen Inhalt an Ihren KI-Anbieter zu senden. Vergewissern Sie sich vor dem Start, dass das nach den Vorgaben Ihres Arbeitgebers oder Kunden zulässig ist.
Was wxKanban erreicht und was nicht
🔒
Ihr Quellcode erreicht wxKanban nicht. Der Dienst erhält die Dokumente, die Ihr Team verfasst — Scopes, Spezifikationen, Pläne, Testergebnisse — dazu Aufgabenkennungen und Dateipfade. Er erhält nicht den Inhalt Ihrer Quelldateien. Das ist eine Eigenschaft der Bauweise des Systems, keine nachträglich aufgesetzte Richtlinie: Die Komponente, die Codeänderungen erzeugt und anwendet, enthält überhaupt keinen Netzwerkclient, und das Prüfwerkzeug für die Codemarkierungen, das Ihren Quellcode einliest, führt keinerlei Netzwerkaufrufe aus.

⚠️
Zwei Wege können Code transportieren, und beide beruhen auf einer Entscheidung. Neither is on by default.
  • Die Remote-Session-Brücke. Eine Entwicklerin oder ein Entwickler, die oder der ausdrücklich eine Remote-Sitzung startet, leitet deren Ausgabe — die regelmäßig Code enthält — an einen separaten Relaisdienst weiter. Freiwillig und abgeschaltet, solange sie nicht von Hand gestartet wird.
  • Dokumente, die Sie verfassen. Spezifikationen und Pläne werden so hochgeladen, wie sie geschrieben sind. Fügt jemand einen Codeauszug in eine Spezifikation ein, reist dieser Auszug als Teil des Dokuments mit. Die Grenze verläuft hier redaktionell — sie hängt davon ab, was Ihr Team niederzuschreiben beschließt.
Ihre eigene Hygiene
Fügen Sie niemals API-Schlüssel, Datenbankpasswörter oder Kundendaten in den KI-Chat ein. Bewahren Sie Geheimnisse in .env auf, das durch .gitignore ausgeschlossen ist.
Halten Sie Ihr Repository privat und überlegen Sie genau, wen Sie einladen.
Die KI führt Git nur aus, wenn Sie es verlangen. In Ihrem Namen wird nichts committet oder gepusht.
