### Why 160 and not the ~198 estimated at the Phase-2A gate

Collapsing was more effective than the estimate assumed. Three mechanisms did the work: equivalence
partitioning (one item per partition rather than per value), boundary items carrying a whole partition
table in `testData` instead of one item per edge, and suite-level items — "all 22 routes require auth"
is one item, not 22. Nothing was dropped for cap pressure (`deferredByCap` is 0), and every
non-instantiated variant carries an explicit reason code rather than being silently absent.

## 6. Risk register

| Risk | Why it matters here | Mitigation in this plan |
|---|---|---|
| A write reaches production | local `.env` points at prod; `TEST_DATABASE_URL` is commented out | CRUD tier runs only on a `wxktest_` clone; `TC-DB-035` asserts `current_schema()` before the first write |
| An unfaithful clone passes tests prod would reject | `INCLUDING ALL` does **not** copy foreign keys | `TC-DB-034` refuses a clone reporting `faithful: false` |
| Under-marked impact ships a defect under a green signoff | migrations/config have no import edges | `TC-FN-065`–`TC-FN-067`, `TC-API-033-N3/N4`, `TC-MCP-007-N1` |
| The two implementations drift | `mcp-server` has its own schema mirror and rule copies | `TC-MCP-010` (schema parity), `TC-MCP-009` (tool parity), and a REST-vs-MCP comparison inside each MCP item |
| A bypass reads as a pass | skip-testing returns `passed: true` | `TC-FN-004`, `TC-API-043`, `TC-UI-012`, `TC-MCP-008-N1` all assert the blocking list stays intact |
| Human time wasted by over-marking | every push bumps `APP_VERSION` | `TC-FN-024` asserts a signoff carries when nothing reached it |

## 7. Test data strategy

No production extract is used, so no anonymisation is required. The CRUD tier seeds a **coherent**
chain — `companies → userprofiles → companyprojects → projectspecifications → testplans` — because the
clone enforces referential integrity exactly as production does and a naive one-row-per-table seed
fails. Volume items generate 10,000 items / 50,000 signoffs and run `ANALYZE` before measuring a plan.

## 8. Data architecture under test (DBA persona)

8 tables from migration `0054`, extended by `0055` (`companyprojects.skiptesting`) and `0056`
(3 foreign keys, 4 `updatedat` columns, 14 covering indexes, 2 redundant indexes dropped).

**Constraint-gap analysis** — rules currently enforced only in application code. These are **findings**,
not tests, and are filed rather than written up as passing data-layer items:

| Rule | Enforced where | Gap |
|---|---|---|
| A machine signoff requires a passing result in that run | `TestSignoffService.signMachine` only | No DB constraint ties a signoff to a `pass` row. A direct INSERT can fabricate a signoff. |
| A human item must be `released` before signoff | `TestSignoffService.signHuman` only | Nothing at the schema level prevents signing an unreleased item. |
| A closed cycle is read-only (FR-050) | `TestCycleService.assertWritable` + the MCP twin | Service-layer only; direct SQL can still write into a superseded cycle. |
| A dismissal belongs to the caller's company | `TestImpactService.dismiss` | No DB-level tenancy; correctness rests on the service resolving three joins. |
| `forcetest` null means inherit | `TestPlanService.resolveForce` | A three-state boolean with no CHECK; a bad write cannot be distinguished from "inherit". |

The first two are the consequential ones: both guard the gate, and both are bypassable by any second
client writing directly to the database — which is exactly the situation this scope anticipates when it
says the runner is swappable.

### CLAR-01 — class-method:TestPlanService.addUserItem

**Question.** A tester adds a test after their set was released. Andy 2026-07-26: it defaults to the NEXT cycle and an admin can roll the cycle back to test to pull it into the current one. Neither behaviour is implemented — addUserItem files the item live into the current plan with released defaulting to false, and there is no rollback control.

**Why it is open.** Answered as a product decision but not yet built, so the item asserts observed behaviour.

**Assumed for now.** Asserted as OBSERVED: the item is created against the current plan and is not offered to testers until the set is released.

**Severity if wrong.** Medium · **Blocks.** TC-API-014, TC-FN-061 · **Filed as.** _not yet filed_

### CLAR-02 — class-method:TestGateService.evaluate

**Question.** FR-044 requires project MEMBERSHIP to read a suite; guardProject only checks that the project is in the caller's company. projectAccess.isUserAssignedToProject exists (spec 011) but is not used by any SCOPE-111 route.

**Why it is open.** Tightening it changes who can read a suite today, which is a product call, so the current items assert company scoping as observed.

**Assumed for now.** Asserted as OBSERVED: company scoping enforced, per-project membership NOT enforced.

**Severity if wrong.** Medium · **Blocks.** TC-API-002-P1 · **Filed as.** _not yet filed_

### CLAR-03 — drizzle-table:testrunresults

**Question.** testrunresults and testitemsubjects deliberately carry no updatedat (both are append-only; testrunresults is documented "never overwritten"). The project convention is createdat+updatedat on every table. Confirm the exemption is intended rather than an oversight.

**Why it is open.** A convention deviation that a future audit will re-raise unless it is recorded as deliberate.

**Assumed for now.** Asserted as OBSERVED: both tables have createdat only, by design.

**Severity if wrong.** Low · **Blocks.** TC-DB-024 · **Filed as.** _not yet filed_
