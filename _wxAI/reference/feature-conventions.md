## Admin Dashboard Conventions

The Admin Dashboard (`src/client/pages/AdminDashboard.tsx`) uses a **single-column Project Overview panel** with per-project document links:

- **Panel header**: "All projects" link (right-aligned) + **"New" button** (opens `CreateProjectModal` for inline project creation, ADMIN only)
- **Project cards**: One `ProjectOverviewCard` per active/branched project showing lifecycle phase progress
- **Per-project document links**: Three `ReportLinkCard` components rendered **inside** each `ProjectOverviewCard` (below the phase list):
  1. **Project Overview** → `/projects/:id/overview` — doctype `ProjectOverview`
  2. **Project Lifecycle** → `/projects/:id/lifecycle` — doctype `ProjectLifecycle`
  3. **Audit Report** → `/projects/:id/audit` — doctype `AuditReport`

Each `ReportLinkCard` shows **"not created"** (indigo, `text-xs`) to the right of the title when the corresponding `projectdocuments` record does not yet exist for that project. Document existence is checked via `GET /api/admin/doc-status`.

**`GET /api/admin/doc-status`** — returns per-project document status:
```json
{
  "projects": {
    "<projectId>": {
      "projectOverview": "<ISO timestamp or null>",
      "projectLifecycle": "<ISO timestamp or null>",
      "auditReport": "<ISO timestamp or null>"
    }
  }
}
```
Queries `projectdocuments` for all projects of the authenticated user's company, checking for `doctype IN ('ProjectOverview', 'ProjectLifecycle', 'AuditReport')` with `specid IS NULL`.

**Adding a new report link**: Add a new `ReportLinkCard` inside `ProjectOverviewCard`, add its `doctype` to the query in `GET /api/admin/doc-status`, and add the corresponding field to each project's status object.

## Project Lifecycle Documents (spec 048)

Lifecycle documentation is **per-project and generated — never hand-edited**. There are two generated per-project documents, each on its own `projectdocuments` doctype. Do **not** create or hand-maintain a repo-wide `specs/projectlifecycle.md` aggregate, and do **not** run `push-lifecycle.mjs` — both were retired in spec 048 (the legacy `GET /api/lifecycle` route, `LifecyclePage`/`LifecyclePanel`, the disk file, and `push-lifecycle.mjs`).

**Doctype `lifecycle` — the auto-updated lifecycle document.**
Generated by the **MCP server** (`mcp-server/src/utils/lifecycle-generator.ts` via `generateProjectLifecycleMarkdown` + `pushLifecycleToDb`) and **refreshed automatically on every scope/spec/task change** — `create_specs` and `implement`/task-sync push an updated, per-project `doctype='lifecycle'` row (DB-only; the hosted server does not write the dev's working tree). This is the live, always-current per-project lifecycle data. Its Phase Distribution uses Mermaid charts (a `pie` for active-phase distribution + an `xychart-beta` bar for all six phases in order — never ASCII bar charts). Nothing should write this doctype by hand.

**Doctype `ProjectLifecycle` — the on-demand PDF (spec 021).**
Generated by `src/server/services/ProjectLifecycleGenerator.ts` from the `projectspecifications` table into per-project markdown **+ PDF** at `specs/projects/<projectid>/projectlifecycle.md`, upserted to `projectdocuments` (doctype `ProjectLifecycle`). Regenerate via `POST /api/admin/projects/:id/lifecycle/regenerate` (admin) or `npx tsx scripts/generate-project-lifecycle.ts --project <id>` (or `--all`). Served as the PDF in the project-details **Lifecycle tab** (`<iframe src="/api/projects/:id/lifecycle">`) and the Admin Dashboard per-project "Project Lifecycle" link. This one is **on-demand / admin-triggered**, not auto-refreshed on CRUD.

**Known follow-up (not yet scoped):** because the Lifecycle tab renders the on-demand `ProjectLifecycle` PDF, it can lag the auto-updated `lifecycle` doc until regenerated. Pointing the tab at the `lifecycle` doctype (or auto-regenerating the PDF on CRUD) is a separate decision flagged in spec 048's Amendment A.

## Development Plan Documents (SCOPE-081)

The **build roadmap** — "where am I, what's built, what next, what's blocking" — is a per-project generated artifact that coexists with the lifecycle docs (it is a *build-order* view; `lifecycle` is a *phase-distribution* view). Two surfaces, mirroring the lifecycle split:

**Doctype `devplan` — the auto-updated deterministic skeleton.**
Generated by the **MCP server** (`mcp-server/src/utils/devplan-generator.ts` via `generateDevplanMarkdown` + `regenerateDevplan`) and **refreshed automatically on every scope/spec/task change** — `create_specs` and `implement`/task-sync call `regenerateDevplan` right alongside `pushLifecycleToDb`/`regenerateScopeFlow`, each in its own fail-open guard (a devplan failure never blocks the op). DB-only on the hosted server. Content is **deterministic, no LLM**: a status-at-a-glance table (state + task %), foundation-up phase grouping (longest-path layering), a phase-grouped Mermaid dependency map, and the critical path — the dependency edges come from the **SCOPE-073 scope-edges resolver** (`buildScopeGraph`, reused). Consumed by the Dev Cockpit "Development Plan" panel via `cockpit_summary`. Nothing writes this doctype by hand.

**The on-demand narrative + PDF — the `dev-plan` skill.**
The judgment layer (the "▶ START HERE" orientation, per-phase exit gates, "what remains") and the print-ready PDF come from the `dev-plan` Claude Code skill (`.claude/skills/dev-plan/`), run on demand. It writes `specs/DEVELOPMENT-PLAN.md` locally and renders the PDF via `scripts/build-devplan-pdf.mjs`. The skill ships to every consumer through the `.claude/skills` kit-sync (exempted from `auditfences` as bundled tooling). The Admin-dashboard "Development Plan" link + viewer follow the `ProjectLifecycle` plumbing exactly (PDF served via iframe + admin regenerate endpoint), and carry the same spec-048-Amendment-A regenerate-to-refresh lag.

## Generated-Output Watermark (SCOPE-082)

Every artifact wxKanban generates on a customer's behalf is stamped with a wxKanban attribution that points downstream readers back to **www.wxperts.com**. It is a **branding / funnel** mark — **not** a tamper-proof control (the visible mark is removable; the invisible zero-width signature is brittle). The real anti-arbitrage levers (pricing / commercial-license tiers, the "done-with-you" philosophy) live outside this scope.

**Three marks on Markdown, applied by one shared helper:**
1. A **frontmatter provenance block** (`wxkanbanGenerator` / `wxkanbanVersion` / `wxkanbanGeneratedAt` / `wxkanbanSource`).
2. A **visible footer** — "Generated with wxKanban — www.wxperts.com · v… · date" (or "Converted with…" for conversion outputs).
3. An **invisible zero-width signature** (`wxk1|G|<version>`).

Rendered **PDFs** additionally carry document metadata (Author/Producer = wxKanban) + a visible per-page footer (`MarkdownPdfRenderer`, via `pdf-lib`).

**Single source of the mark:** `@wxkanban/watermark` (`shared/watermark`, mirrors `@wxkanban/preflight`) exports `stampMarkdown` / `verifyMarkdown`. A **byte-compatible Python port** (`shared/watermark/python/wxkanban_watermark.py`) is used by the conversion skills. Stamping is **idempotent** (no double-stamp) and **fail-open** (never blocks generation).

**Surfaces stamped:** MCP `lifecycle` + `devplan` generators; app `ProjectLifecycleGenerator` / `DevelopmentPlanGenerator` / project-overview; skill-pushed `ScopeAnalysis` / `ProjectScopeAnalysis` (stamped in the MCP `upsert_document` handler); and the `wxConversion` / `cwConversion` / `vbConversion` per-element Markdown + scope/stub/ER outputs (Python helper, shipped via kit-sync to all 3 skill-mirror dirs).

**Manual stamp / verify:** `npm run watermark verify <file>` / `npm run watermark stamp <file> [--write]` (CLI `scripts/watermark.mjs`; command doc `_wxAI/commands/watermark.md`). Use when a generator is bypassed or a doc is hand-authored.

## Subscription-Aware Help (SCOPE-084)

The Help system documents every app area/feature and shows its per-plan availability across the four **public** plans (Single User, Small/Medium Business, Consultant, Enterprise) — *included*, *not included*, or *upgrade-required* — from one catalog.

- **Single source of truth:** `src/shared/help/catalog.ts` — the typed catalog (`PLANS`, `HELP_FEATURES` each with a `minPlan`, `CATEGORIES`, `availabilityFor`, `billingPlanToPublicPlan`). Shared by the API, the in-app page, and the standalone build. **Edit availability HERE**, then rerun the drift test.
- **Authoritative mapping:** Small/Medium Business is the baseline; **Time Tracking & Billing, Invoices, and Reports are Consultant+** (NOT on Single User or Small Business). Where this disagrees with `TierEnforcementService` feature flags, the catalog wins (see reconciliation below).
- **In-app page:** `/help` → `src/client/pages/PlanHelpPage.tsx` (+ `src/client/components/help/*`), in the dashboard nav for **all tiers** (LifeBuoy icon, `appnav.help` in all 6 locales). Fetches `GET /api/help/catalog` to default the tier selector to the viewer's plan; falls back to the compiled-in catalog if the fetch fails.
- **API:** `GET /api/help/catalog` (viewer plan + catalog) and `POST /api/admin/help/regenerate` (admin; body `{ projectId }`) in `src/server/routes/helpCatalog.ts`, mounted at `/` **before** the `/api/help` articles router. This is **distinct** from the SCOPE-044/066 `/api/help` articles/FAQ system in `routes/help.ts` — don't confuse them.
- **Stored doc (`doctype='help'`):** `src/server/services/HelpGenerator.ts` renders the catalog to Markdown and upserts a single canonical `doctype='help'` row on a project via `ProjectDocumentService.upsertDocument` (watermarked). Trigger through the admin regenerate endpoint.
- **Standalone page:** `public/help.html`, generated by `scripts/build-help-html.mts` (`npx tsx scripts/build-help-html.mts`) — the public/prospect mirror, fully self-contained.
- **Drift guard:** `src/server/services/helpDrift.ts` (`checkHelpDrift` / `unexpectedHelpDrift`) compares the catalog to `TierEnforcementService.TIER_CONFIG`; `tests/unit/helpCatalog.test.ts` fails on any drift beyond the two accepted divergences.

**Reconciliation follow-up (separate bug — NOT this scope):** `TierEnforcementService.TIER_CONFIG` sets the `time_tracking` flag on `SMALL_BUSINESS` and omits `pm_integration` from `SMALL_BUSINESS`. Both diverge from the customer-facing mapping and should be corrected in the tier config. Until then the Help catalog is authoritative and `helpDrift` flags these two as *accepted* divergences.
